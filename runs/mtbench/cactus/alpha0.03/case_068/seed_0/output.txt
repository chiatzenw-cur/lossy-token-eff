We have two already‑sorted arrays `A` (size `m`) and `B` (size `n`).  
We have to return the *k‑th smallest* element that would appear if we
merged the two arrays and sorted the result.  
The requirement is *linear complexity*, i.e. we want an algorithm whose
running time grows proportionally to `k` (and never to `m+n` in the
worst case).  

The simplest method is to **walk through the merge process only as far
as necessary** – exactly the same idea that the merge step of mergesort
uses until it has produced `k` elements of the sorted order.  

Because we stop after the k‑th element, the running time never exceeds
`k` steps, i.e. and it is `O(k)` time and `O(1)` extra space.

--------------------------------------------------------------------

### Algorithm
```
let i = 0          // index in A
let j = 0          // index in B
let last = None    // will hold the k-th element

for step from 1 to k:
    if i < m and (j >= n or A[i] <= B[j]):
        last = A[i]
        i += 1
    else:
        last = B[j]
        j += 1

return last
```

*If `k` is 1‑based, the element returned is the one‐based k‑th smallest.  
If you prefer 0‑based indexing, just change `for step in 0 … k-1`.*

--------------------------------------------------------------------

### Correctness Proof

We prove that the algorithm returns the k‑th smallest element of the
multiset `A ∪ B`.

1. **Invariant**  
   At the beginning of each loop iteration, *all* elements that have
   been examined so far are smaller than or equal to `last`.  
   Initially no element is examined: the invariant holds trivially.

2. **Maintenance**  
   In each iteration we compare the current elements `A[i]` equal to
   `i`‑th unchecked element of `A` and `B[j]` equal to `j`‑th unchecked
   element of `B`.  
   * If `A[i] <= B[j]`, then `A[i]` is the smallest of the two
     *remaining* elements, and we set `last = A[i]`.  
     We then increment `i` – the element `A[i]` is now *used* and will
     never be considered again.  
   * The other branch is analogous for `B[j]`.  
   In either case the invariant remains true because we always choose
   the *smallest* unused element and add it to `last`.  
   After the iteration, `last` is the smallest element among all
   *currently** remaining* elements, hence the invariant holds for
   the next iteration.

3. **Termination**  
   After `k` iterations, exactly `k` elements have been taken from the
   two arrays.  
   By the invariant, `last` is the largest of those chosen elements,
   and all other not yet chosen elements (if any) are larger or equal
   to `last`, because the algorithm chose the smallest at every step.
   Therefore `last` is precisely the k‑th smallest element of the union.

Hence the algorithm is correct. ∎

### Reference Implementation (Python 3)

```python
def kth_smallest_sorted(a: list[int], b: list[int], k: int) -> int:
    """
    Return the k-th smallest element in the union of two sorted arrays a and b.
    Parameters
    ----------
    a : list[int]
        First sorted list (non‑decreasing).
    b : list[int]
        Second sorted list (non‑decreasing).
    k : int
        1‑based rank (1 <= k <= len(a)+len(b))

    Returns
    -------
    int
        The k‑th smallest element.

    Raises
    ------
    ValueError
        If k is out of bounds.
    """
    m, n = len(a), len(b)
    if k < 1 or k > m + n:
        raise ValueError(f"k={k} is out of bounds for total length {m+n}")

    i, j = 0, 0          # indices in a and b
    last: int | None = None

    for _ in range(k):
        if i < m and (j >= n or a[i] <= b[j]):
            last = a[i]
            i += 1
        else:
            last = b[j]
            j += 1

    # last is guaranteed to be set because k >= 1
    return last
```
